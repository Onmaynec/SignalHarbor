# История версий

## v0.4.0 — Performance & Stability

### Производительность
- Worker группирует новые события одного пакета по rule/service/environment/selected labels, проверяет каждый fingerprint один раз вместо пересчёта окна для каждого события. Полная запись в outbox, ACK и сохранение транзакции не меняются.
- Правила count_error и error_rate теперь получают общее количество событий и ошибок одним агрегирующим запросом вместо двух отдельных COUNT.
- Извлечение связанных events и правил для очередного пакета выполняется пакетными запросами. Порядок захвата fingerprint locks стабильный, чтобы снизить риск перекрёстных блокировок.
- Настройка WORKER_BATCH_SIZE (1–500, стандартно 250) управляет размером транзакционного пакета. Для увеличения параметра требуется контроль задержек БД.

### Устойчивость
- Схема PostgreSQL обновляется с v2 до v3; добавлена таблица worker_status с постоянной информацией об экземплярах worker.
- Worker раз в ~5 секунд записывает heartbeat, суммарное число обработанных задач и ошибок. При перезапуске worker получает новый идентификатор, старый помечается неактивным по времени последнего heartbeat.
- В /api/v1/ops добавлены активные worker, готовые к обработке и отложенные по timestamp задания, список последних worker с counters/last seen.
- Новая информация отображается в административной «Диагностике».
- Интеграционные тесты: свёртывание сотен событий в одну оценку правила, сохранение разделения по labels, откат всего пакета при искусственной ошибке, конкурентное получение outbox разными worker, хранение heartbeat и исключение future events из ready backlog.

### Проверки и границы
- Нагрузочный p95 на 2000 событий/мин за 30 минут не подтверждён: текущие тесты проверяют корректность и уменьшение числа вызовов, но не подтверждают целевой SLO.
- Нет подтверждённых экспериментов kill -9 контейнеров и E2E SSE через настоящий сетевой обрыв; это остаётся в открытых Issues.
- Нет полного 180/365-дневного retention и многорепликового rate-limit. Не считать продукт принятым по PV-OPS-04.

## v0.3.0 — Detection & Observability

### Detection
- Для входящих событий с допустимым опозданием до 120 секунд расчёт окна учитывает event-time watermark выбранной группы. События с кратким окном больше не теряются только потому, что пакет доставлен с задержкой.
- События с отметкой времени в будущем сохраняются вместе с durable outbox и остаются необработанными до наступления их времени. Это устраняет прежний сценарий потери будущего события при преждевременной обработке.
- Для каждого alert fingerprint добавлена транзакционная блокировка перед созданием записи. Уникальное ограничение остаётся защитой на уровне PostgreSQL.
- Первое срабатывание алерта теперь записывает в timeline detectionLagMs относительно времени приёма того события, которое привело к обнаружению.

### Observability
- В административном GET /api/v1/ops добавлены постоянные показатели PostgreSQL: backlog, возраст старейшей ожидающей задачи, число обработанных outbox и принятых событий за час, число late events, оценка p95 задержки обнаружения.
- В веб-панели администратора появился раздел «Диагностика» с состоянием очереди и метриками обнаружения.
- Пробные SSE-подключения теперь повторно проверяют действительность сессии и текущую команду при каждом опросе. После отзыва сессии генератор прекращает отдачу данных.
- Добавлены интеграционные тесты на опоздавшие/будущие события, группировку fingerprint, диагностику, SSE cursor и отзыв сессии.

### Известные ограничения
- Значение p95 в /api/v1/ops — ближайший ранг на выборке максимум из 5000 событий первого firing за час, а не доказательство SLO p95 ≤ 10 секунд.
- По-прежнему нет полноценного 30-минутного нагрузочного прогона 2000 событий/мин.
- SSE-протокол и повторная авторизация проверяются тестами на уровне приложения, но реальный сквозной reconnect при обрыве сети не подтверждён.
- 180-дневное хранение агрегатов, 365-дневный срок metadata и межрепликовый rate-limit ещё в работе.
- Изменений в схеме БД нет: остаётся v2, новая миграция не требуется.

## v0.2.0 — Reliability Update

### Новое
- Введён транзакционный механизм миграций со стабильными версиями схемы.
- Миграция v2 добавляет частичный уникальный индекс на активный incident в пределах team/service/environment, индекс pending outbox и индекс неподтверждённых incident.
- Миграции на PostgreSQL сериализованы через advisory lock. Существующие БД без schema_version блокируются до ручной проверки, а не переписываются автоматически.
- Два worker, одновременно открывающие incident одного окружения, используют транзакционный advisory lock до первой вставки.
- Retention пропускает устаревшие ingest events с необработанными outbox tasks и очищает просроченные сессии.
- Добавлены регрессионные тесты на повтор миграции, обнаружение конфликтующих старых данных, конкурирующие worker, уникальность scope и сохранность pending outbox.

### Обновление с v0.1.0
1. Сделать pg_dump и проверить возможность восстановления.
2. Убедиться, что в БД нет нескольких активных incidents одного team/service/environment. Если есть, завершить ручной разбор: перенести информацию, решить судьбу связанных alert/timeline и только затем закрыть лишний incident.
3. Выполнить docker compose up --build -d — сервис migrate применит v2 до запуска API/worker.
4. Проверить docker compose logs migrate api worker и docker compose exec api python -m signalharbor.manage migrate: повторный вызов безопасен.
5. Провести пробный restart worker после принятого ingest события и проверить отсутствие дублирования.

### Не закрыто
- Нет подтверждённого теста на 2000 events/min в течение 30 минут и метрик p95.
- Нет полноценного retention агрегатов на 180 дней и metadata инцидентов на 365 дней.
- Не проведён сквозной SSE reconnect/fault-injection после kill -9 и E2E пяти ролей.
- Многоузловой rate-limit и полноценный event-time watermark ещё не реализованы.

Полное выполнение PV-OPS-04 подтверждается только при закрытии всех Must требований и AT-01–AT-12. Разделы [приёмка](docs/acceptance.md) и [эксплуатация](docs/runbook.md) отражают текущие ограничения.
