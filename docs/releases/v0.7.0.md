# SignalHarbor v0.7.0 — Event-Time Detection & Alert Accuracy

Релиз посвящён воспроизводимости rule engine, корректной идентификации alert и поведению при частых переходах между firing/recovered.

## Event-time и порядок доставки

- Watermark для count_error/error_rate продолжает использовать максимальный timestamp допустимой группы service/environment/rule/selected labels. Добавлена единая нормализация отсутствующей выбранной label: пустая строка в fingerprint и COALESCE в SQL.
- Добавлены сценарии 60-секундного окна, где события старше порога окна поступают в обратном порядке, но остаются в пределах 120-секундного допуска. В обоих порядках итоговые value/count и границы окна одинаковы.
- Для каждой оценки alert сохраняются `window_start_at` и `window_end_at`. Миграция v5→v6 добавляет nullable поля, существующие alert заполняют их при следующей оценке.

## Fingerprint и event explorer

- GET `/api/v1/events?fingerprint=...` ограничивает выдачу service/environment, сохранёнными label values и точными границами окна alert.
- Учитывается семантика исторической версии правила: `count_error` выдаёт только ошибки, `error_rate` — все события окна, `heartbeat_missing` — heartbeat до конца интервала.
- При отсутствии записи старой `RuleRevision` перед первым редактированием legacy-правила сохраняется снимок прежней конфигурации.

## Обновление правил и flapping

- При изменении порога/окна/cooldown/recovery/severity с прежней группировкой активные alert переоцениваются и получают новую `rule_version`; изменение фиксируется в timeline.
- Изменение service/environment/kind/groupLabels или отключение правила закрывает прежнее поколение alert с `alert_reconfigured`. Старое поколение не переоткрывается периодическим сканированием.
- Если событие во время cooldown снова подняло значение выше порога, recovered alert текущей версии повторно оценивается после истечения cooldown. При сохраняющемся условии alert переходит в firing и пишет `refired`; без такого события старые recovered alert не опрашиваются постоянно.
- Сохранены независимые переходы error и heartbeat правил и прежняя политика maintenance.

## Проверки

Новые интеграционные сценарии:
- одинаковый результат короткого event-time окна при старых/новых событиях в разном порядке;
- отдельные группы для отсутствующей label и заданного значения;
- точная фильтрация count_error и error_rate по fingerprint;
- обновление rule_version активного alert;
- завершение старого поколения после смены grouping и сохранение старого event window;
- повторная оценка после cooldown;
- чередование error и heartbeat с независимым восстановлением.

CI запускает PostgreSQL 16, полный pytest, Ruff, compileall, node --check и docker compose config.

## Обновление

1. Сделайте резервную копию PostgreSQL.
2. Обновите код: `git pull origin main`.
3. Пересоберите сервисы: `docker compose up --build -d`.
4. Убедитесь, что migrate завершился успешно и `/health/ready` отвечает.
5. Для старых alert без сохранённых границ event window поля будут заполняться при следующей оценке; до этого используется совместимый fallback от fired_at и версии правила.

## Что остаётся открытым

Релиз закрывает реализационную часть Issue #5 в рамках автоматизированных сценариев, но не означает полную приёмку PV-OPS-04. Не подтверждены AT-10 (2000 events/min в течение 30 минут с p95 ACK/detection), реальный fault-injection kill/restart, сетевой SSE reconnect, backup/restore и полный E2E RBAC. Issues #1–#4 остаются открытыми.
