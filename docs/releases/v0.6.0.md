# SignalHarbor v0.6.0 — Production Hardening

Обновление защиты аккаунтов и границ ingest при горизонтальном масштабировании.

## Двухфакторная аутентификация TOTP

- Добавлена добровольная MFA на основе RFC 6238 (6 цифр, шаг 30 секунд, окно ±1 шаг) для всех ролей.
- В профиле «Безопасность» пользователь может запустить настройку с повторным вводом пароля, получить секрет/otpauth URI и подтвердить его кодом из приложения.
- TOTP-секреты хранятся в PostgreSQL только в зашифрованном виде с Fernet. Обязателен операторский секрет MFA_ENCRYPTION_KEY, не содержащийся в исходном коде.
- После подключения выдаются 8 одноразовых резервных кодов, сохраняются только их SHA-256 хеши. Коды показываются только один раз.
- При новом входе с включённой MFA обязательно подтвердить пароль и одноразовый код или резервный код. Прежние TOTP-коды одного временного шага не переиспользуются; резервный код погашается в транзакции выдачи сеанса.
- Подключение MFA отзывает другие пользовательские сеансы. Отключение требует пароль и второй фактор, отзывает все сеансы и требует повторного входа.
- Отсутствие/неверный ключ шифрования не отключает MFA: вход с уже активированной защитой отклоняется по принципу fail-closed (503).

## Общий ingest rate-limit

- Вместо счётчика в оперативной памяти каждого API-процесса PostgreSQL хранит окно квоты по ingest key.
- Параллельные API-процессы синхронизируют резервирование квоты через PostgreSQL advisory transaction lock.
- Резервирование квоты и запись Event + Outbox включены в одну транзакцию. Невалидное событие не расходует квоту после rollback. HTTP 429 возвращает Retry-After.
- SQLite сохраняет локальный fallback и не используется как производственная многорепликовая БД.

## Схема и тестирование

- Версионированная миграция v4 → v5: таблицы mfa_credentials, mfa_enrollments и ingest_quotas.
- Новые регрессии проверяют enrollment, секреты и резервные коды, блокировку повтора TOTP, fail-closed без ключа, отзыв сеансов, лимит при последовательных и конкурентных запросах, rollback при invalid payload, восстановление старой схемы.

## Как обновиться

1. Создайте и проверьте резервную копию PostgreSQL.
2. Обновите исходники: git pull origin main.
3. При планировании MFA сгенерируйте устойчивый Fernet-ключ:
   python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
4. Укажите MFA_ENCRYPTION_KEY в .env, храните его отдельно от базы и не коммитьте. Для существующей включённой MFA ключ обязан совпадать с ключом исходной установки.
5. Запустите docker compose up --build -d, проверьте статус migrate и /health/ready.
6. Войдите в приложение → «Безопасность» → подключите приложение-аутентификатор, сохраните резервные коды офлайн.

MFA необязательна, пока пользователь сам её не включил. Параметр MFA_ENCRYPTION_KEY требуется для настройки и использования MFA, но не для обычной работы системы без включённых MFA-аккаунтов.

## Не завершено

Не выполнены полноценный 30-минутный тест 2 000 events/min с подтверждённым p95, network-level throttling, WebAuthn и обязательная MFA-политика по ролям, реальные fault-injection испытания kill/restart контейнеров, восстановление из бэкапа и полная сквозная E2E матрица пяти ролей. Повторное шифрование/ротация MFA_ENCRYPTION_KEY пока не автоматизированы. Проверка PV-OPS-04 остаётся незавершённой.
