# Модель угроз и границы доверия

**Активы:** токены ingest, сессионные токены, список сервисов, payload событий, инциденты, графики дежурств.

**Доверие:** ingest-источник знает ключ, ограниченный конкретным окружением. Пользовательский сеанс с HttpOnly cookie и SameSite=Strict авторизует операции с собственными сервисами/командами. База и worker — доверенная зона. Браузер и все входные JSON — недоверенные.

**Защитные механизмы (состояние v0.7.0):**
- Ключи и сессионные токены хранятся как SHA-256 хеш, исходный ключ показывается только при создании.
- Пароли: PBKDF2-HMAC-SHA256 с уникальной случайной солью и 390000 итерациями.
- Подпись запроса на состояние обеспечена отдельным cookie csrf и заголовком X-CSRF-Token; формы по умолчанию не могут создать такой запрос cross-site.
- Вся видимость сущностей ограничена командой серверным запросом и проверкой целевой сущности (включая SSE, events, metrics, timeline). Observer получает статусные сведения без внутренних payload, owner, полного timeline, правил и содержимого событий.
- Неограниченная вложенность/размер входящего JSON недопустимы; каждый запрос ограничен 1 MiB, батч — 500 событий, type и labels — отдельно.
- Renderer UI экранирует пользовательские значения, не вставляет сырые payload как HTML.
- Учтены 401, 403, 404, 409, 429 и формализованный error-envelope с requestId.
- Raw secret нигде не логируется и не выдается через GET API.
- POST `/api/v1/login`: общий PostgreSQL-лимит на нормализованный email (8 неверных паролей / 15 минут → блокировка на 15 минут, 429 + Retry-After); состояние в таблице `login_attempts` по SHA-256 хешу email. Проверка неизвестного пользователя использует фиктивный PBKDF2 hash. Счётчик очищается при успешном входе.
- Для JSON API и SSE установлен `Cache-Control: no-store`, чтобы промежуточный кэш не сохранял чувствительные ответы.
- Fingerprint query повторно проверяет team scope и ограничивает события service/environment, event-time window, выбранными labels и типом исторической версии правила; неизвестный fingerprint не раскрывает чужие данные.
- Архивная статистика хранит только числовые счётчики per team/service/environment/hour без labels, secrets и payload. Исторический API разграничивает доступ по team и не доступен observer.
- TOTP-секреты хранятся зашифрованными Fernet с отдельным `MFA_ENCRYPTION_KEY` в окружении, а recovery codes — в виде хешей SHA-256. Код TOTP одного временного шага и каждый recovery code принимаются не более одного раза. Отсутствие ключа при активной MFA приводит к 503, а не к пропуску второго фактора. Потеря ключа требует операторского восстановления, автоматической ротации нет.
- При включении MFA другие сеансы пользователя отзываются; отключение с паролем и фактором отзывает все сеансы. Для TOTP доступна добровольная страница «Безопасность».
- Лимит ingest на каждый ключ теперь хранится в PostgreSQL (`ingest_quotas`): advisory transaction lock исключает превышение из-за двух одновременных API реплик; невалидный ingest откатывает квоту и событие вместе.

Публичный endpoint /status закрыт по умолчанию: если PUBLIC_STATUS_SERVICE_IDS не задан, он не возвращает ни одного сервиса. Параметр требует явного списка разрешённых ID.

**Операционные требования:** сменить все пароли в .env; за reverse proxy включить TLS и COOKIE_SECURE=true; ограничить HTTP 8080 firewall и не публиковать API наружу без TLS. Заголовок X-Forwarded-For не используется для авторизации.

**Известные риски (нужны перед production):**
- Ingest лимит теперь общий для нескольких реплик через PostgreSQL, но сетевой rate-limit по IP, API gateway throttling и защита от распределённых DoS не реализованы.
- MFA на TOTP реализована как добровольная настройка пользователя; принудительная MFA по ролям, WebAuthn, безопасный сброс MFA оператором и сетевой throttling для большого числа разных email пока отсутствуют. Аккаунтные lockouts сохраняют риск DoS против известного email; reverse proxy rate-limit обязателен для внешнего доступа.
- Отсутствует обязательное шифрование payload в DB на уровне приложения; использовать disk encryption.
- В выдаче событий используется связка fingerprint→service/env, а не точное правило/labels в фильтре. Не считать фильтр точным forensic query до расширения схемы.
- Бизнес-логика не рассчитана на враждебно подделанные client timestamps сверх диапазона ±2 минуты / 30 дней.
- Приватные payload удаляются по raw retention 30 дней, но не реализованы автоматическое удаление по индивидуальному запросу и отдельная антивирусная проверка вложений (вложения не принимаются).

Любое изменение RBAC требует отдельного интеграционного теста на доступ к чужим сущностям.
