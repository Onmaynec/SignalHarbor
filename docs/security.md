# Модель угроз и границы доверия

**Активы:** токены ingest, сессионные токены, список сервисов, payload событий, инциденты, графики дежурств.

**Доверие:** ingest-источник знает ключ, ограниченный конкретным окружением. Пользовательский сеанс с HttpOnly cookie и SameSite=Strict авторизует операции с собственными сервисами/командами. База и worker — доверенная зона. Браузер и все входные JSON — недоверенные.

**Защита, реализованная в v0.1.0:**
- Ключи и сессионные токены хранятся как SHA-256 хеш, исходный ключ показывается только при создании.
- Пароли: PBKDF2-HMAC-SHA256 с уникальной случайной солью и 390000 итерациями.
- Подпись запроса на состояние обеспечена отдельным cookie csrf и заголовком X-CSRF-Token; формы по умолчанию не могут создать такой запрос cross-site.
- Вся видимость сущностей ограничена командой серверным запросом и проверкой целевой сущности (включая SSE, events, metrics, timeline). Observer получает статусные сведения без внутренних payload, owner, полного timeline, правил и содержимого событий.
- Неограниченная вложенность/размер входящего JSON недопустимы; каждый запрос ограничен 1 MiB, батч — 500 событий, type и labels — отдельно.
- Renderer UI экранирует пользовательские значения, не вставляет сырые payload как HTML.
- Учтены 401, 403, 404, 409, 429 и формализованный error-envelope с requestId.
- Raw secret нигде не логируется и не выдается через GET API.

**Операционные требования:** сменить все пароли в .env; за reverse proxy включить TLS и COOKIE_SECURE=true; ограничить HTTP 8080 firewall и не публиковать API наружу без TLS. Заголовок X-Forwarded-For не используется для авторизации.

**Известные риски (нужны перед production):**
- Лимит основан на памяти одного API процесса: мульти-репликация требует Redis/DB atomic buckets.
- Нет блокировки подбора пароля и MFA; внешнюю публикацию без reverse proxy rate limiting запрещаем.
- Отсутствует обязательное шифрование payload в DB на уровне приложения; использовать disk encryption.
- В выдаче событий используется связка fingerprint→service/env, а не точное правило/labels в фильтре. Не считать фильтр точным forensic query до расширения схемы.
- Бизнес-логика не рассчитана на враждебно подделанные client timestamps сверх диапазона ±2 минуты / 30 дней.
- Не реализованы отдельные политики удаления конфиденциальных payload и антивирусная проверка вложений (вложения не принимаются).

Любое изменение RBAC требует отдельного интеграционного теста на доступ к чужим сущностям.
